Задача: единая стратегия обработки ошибок и логирования во всех NestJS-микросервисах монорепозитория.

Этап 1. Аудит (без изменений кода).
- Перечисли все сервисы (apps/* или services/*) и точки входа: HTTP-контроллеры, message/event-обработчики.
- Для каждого сервиса зафиксируй: где сейчас бросаются исключения, где они перехватываются, используются ли HttpException, RpcException, голый throw new Error(), console.log, есть ли глобальный ExceptionFilter и логгер.
- Составь таблицу «сервис → текущее состояние → проблемы». Не переходи к этапу 2, пока таблица не готова.

Этап 2. Проектирование (предложи 2 варианта, сравни по критериям: объём изменений, совместимость контрактов, тестируемость, расходы на поддержку).
- Таксономия ошибок: базовый класс AppError (code, httpStatus, isOperational, context, cause) и наследники по доменным категориям (NotFound, Validation, Conflict, Unauthorized, Forbidden, ExternalService, Internal).
- Разделение операционных ошибок (ожидаемых) и программных дефектов (непредвиденных).
- Граница обработки: HTTP — глобальный ExceptionFilter; RPC/события — отдельный фильтр или перехватчик, использующий RpcException с тем же кодом.
- Логирование: структурированный логгер (JSON), уровни: 4xx → warn без стека; 5xx и программные дефекты → error со стеком только в логе; requestId/correlationId через AsyncLocalStorage; редактирование чувствительных полей.
- Общая библиотека или пакет в монорепозитории (например, packages/errors) против копирования в каждый сервис — обоснуй выбор.

Этап 3. Реализация после подтверждения варианта.
- Сначала пакет ошибок и фильтры, затем подключение в сервисы по одному, с тестами на каждый сервис.

Ограничения:
- Стек трейса never попадает в тело ответа клиенту, в любом режиме окружения.
- Ответ клиенту: { code, message, requestId }. Текст сообщения понятен пользователю и не раскрывает внутреннего устройства.
- Одна ошибка логируется один раз — на границе, а не на каждом уровне.
- Существующие контракты API не ломаются без явного согласования; изменения фиксируются в списке.
- Каждое изменение сопровождается тестом (unit на маппинг ошибок, e2e на ответ).

Вывод по каждому этапу: краткий отчёт с перечнем файлов, рисками и открытыми вопросами.
