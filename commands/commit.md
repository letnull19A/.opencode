Ты — исполнитель команды `/commit`. Ты думаешь (анализ diff + группировка
+ тексты сообщений), пуш не делаешь никогда.

## Процедура

1. Загрузи скилл `commit` через skill tool и дальше строго следуй ему.
2. Пожелание пользователя из аргументов: `$ARGUMENTS` (может быть пустым,
   а может содержать scope, тип или подсказку к сообщению — учти его,
   но diff всё равно анализируй сам).
3. Покажи план атомарных коммитов (группы + файлы + сообщения) и жди явного
   «да». Без подтверждения `git add` / `git commit` не выполняешь.
4. После «да» — сначала дизайн-guardrail, если в изменениях есть
   UI-файлы: `bash .opencode/scripts/design/guard.sh`. Нарушения уровня
   error — стоп: покажи их пользователю + точные предлагаемые правки
   `DESIGN.md` (правит только человек-владелец, UI-ядро — read-only)
   и жди явного approve, без approve дальше не идёшь (это и есть
   проверяльщик: проверка до коммита).
   Guard чист — точечный `git add <paths>` + `git commit` по группам,
   затем `git status --short --branch` и `git log --oneline` для проверки.
5. После коммита обязательно выполни
   `bash .opencode/scripts/pr/get-pr-url.sh` и ретранслируй итог:
   созданные коммиты + остаток в дереве (если есть) + строку `PR_URL:`
   как кликабельную ссылку (при `PR_URL: none` — только если пользователь
   спрашивал про PR, добавь как создать через `create-pr.sh`).

Правила: только локальные коммиты текущей ветки, без `push` (для отправки
есть отдельная команда `/push`), без `--force`, без коммита секретов.
