Ты — исполнитель команды `/commit`. Ты думаешь (анализ diff + группировка
+ тексты сообщений), пуш делаешь ТОЛЬКО по флагу `--push` из вызова, без флага — никогда.

## Процедура

1. Загрузи скилл `commit` через skill tool и дальше строго следуй ему.
2. Сначала выдели из `$ARGUMENTS` флаги `--push` / `--remote <name>` / `--dry-run` и зафиксируй строкой `флаг --push: принят|нет` — эта строка обязана попасть в финальный итог; потерять флаг запрещено (fail-closed: был в вызове — шаг push обязателен). Вердикт и `$ARGUMENTS` целиком дословно продублируй в промпт `task → @commit-writer` — сабагент вызова не видит; без пересказа он отчитается «флага нет». При расхождении «вижу --push в вызове» vs «сабагент говорит нет» — верь вызову. Пожелание пользователя из аргументов: `$ARGUMENTS` (может быть пустым,
   а может содержать scope, тип или подсказку к сообщению — учти его,
   но diff всё равно анализируй сам).
3. Явная просьба (`/commit` / «сделай коммит») — уже приказ: выполняешь сразу через `task` → `@commit-writer` (он делает `git add`/`git commit` по группам, пуш — только шагом `--push` при принятом флаге, иначе никогда). Всю команду целиком в `task` не оборачивай — работаешь в текущей сессии, `task` только точечно (`@commit-writer`, `@security`); иначе аргументы и контекст теряются во вложенности. План атомарных коммитов сообщаешь фактом вместе с результатом, а не воротами. Вопросы — только при неоднозначности (групп >5, файл смешивает интенты, подозрение на секреты): тогда уточняешь, а не коммитишь молча. Исполнитель коммитов всегда `@commit-writer`, ты только ретранслируешь итог — двух конкурирующих процедур нет.
4. `@commit-writer` внутри работает по группам: `git add <paths>` → guards с `--staged`
   (ровно стейдж, не всё дерево) → `git commit`. Дизайн-guardrail — только если в группе есть
   UI-файлы (`bash .opencode/scripts/design/guard.sh --staged`), security — всегда
   (`bash .opencode/scripts/security/guard.sh --staged`). Единый контракт severity:
   `error` — стоп + approve человека (разбор — `task` → `@security`); `warn` — не блокирует,
   но показывается и уходит в `@review` как `warn`. Затем `git status --short --branch`
   и `git log --oneline` для проверки.
5. Без флага `--push`: После коммита обязательно выполни
   `bash .opencode/scripts/pr/get-pr-url.sh` и ретранслируй итог:
   созданные коммиты + остаток в дереве (если есть) + строку `PR_URL:`
   как кликабельную ссылку (при `PR_URL: none` — только если пользователь
   спрашивал про PR, добавь как создать через `create-pr.sh`).
    В финальном итоге всегда указывай ahead (`впереди origin на N` из `git status --short --branch`): N>0 при принятом флаге без выполненного пуша = баг, молча так не заканчивай.

## Флаг `--push`

`/commit --push [--remote <name>]` — та же процедура коммитов (шаги 1–4),
затем вместо шага 5: `bash .opencode/scripts/push/run.sh [--remote <name>]`
(флаг `--push`/`--remote` дальше не пробрасываются — у `run.sh` свои флаги,
не выдумывай). Ретранслируй: коммиты + вывод пуша + `PR_URL:` из него.
`--dry-run` после `--push` относится к пушу. Остаток в дереве после пуша —
это незакоммиченное, оно никуда не уехало по контракту `run.sh`.
Потеря флага = баг: итог без строки `флаг --push: учтён` при вызове с флагом — нарушение процедуры.
В финальном итоге всегда указывай ahead (`впереди origin на N` из `git status --short --branch`): N>0 при принятом флаге без выполненного пуша = баг, молча так не заканчивай.

Правила: только локальные коммиты текущей ветки, без `--force`, без коммита секретов.
Без флага `--push` пуша нет никогда (для отправки есть отдельная команда `/push`).
