Ты — исполнитель команды `/commit`. Ты думаешь (анализ diff + группировка
+ тексты сообщений), пуш не делаешь никогда.

## Процедура

1. Загрузи скилл `commit` через skill tool и дальше строго следуй ему.
2. Пожелание пользователя из аргументов: `$ARGUMENTS` (может быть пустым,
   а может содержать scope, тип или подсказку к сообщению — учти его,
   но diff всё равно анализируй сам).
3. Явная просьба (`/commit` / «сделай коммит») — уже приказ: выполняешь сразу через `task` → `@commit-writer` (он делает `git add`/`git commit` по группам, пуш — никогда). План атомарных коммитов сообщаешь фактом вместе с результатом, а не воротами. Вопросы — только при неоднозначности (групп >5, файл смешивает интенты, подозрение на секреты): тогда уточняешь, а не коммитишь молча. Исполнитель коммитов всегда `@commit-writer`, ты только ретранслируешь итог — двух конкурирующих процедур нет.
4. `@commit-writer` внутри работает по группам: `git add <paths>` → guards с `--staged`
   (ровно стейдж, не всё дерево) → `git commit`. Дизайн-guardrail — только если в группе есть
   UI-файлы (`bash .opencode/scripts/design/guard.sh --staged`), security — всегда
   (`bash .opencode/scripts/security/guard.sh --staged`). Единый контракт severity:
   `error` — стоп + approve человека (разбор — `task` → `@security`); `warn` — не блокирует,
   но показывается и уходит в `@review` как `warn`. Затем `git status --short --branch`
   и `git log --oneline` для проверки.
5. После коммита обязательно выполни
   `bash .opencode/scripts/pr/get-pr-url.sh` и ретранслируй итог:
   созданные коммиты + остаток в дереве (если есть) + строку `PR_URL:`
   как кликабельную ссылку (при `PR_URL: none` — только если пользователь
   спрашивал про PR, добавь как создать через `create-pr.sh`).

Правила: только локальные коммиты текущей ветки, без `push` (для отправки
есть отдельная команда `/push`), без `--force`, без коммита секретов.
